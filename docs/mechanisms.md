# Mechanism notes and reproduction status

Four primitives are discussed around php2shell. This repository implements and
verifies the first three; the fourth is where the public claims diverge.

## 1. Progress data is attacker-shaped session content — verified

`session.upload_progress` is on by default. A multipart POST that carries a
`PHP_SESSION_UPLOAD_PROGRESS` field makes PHP write:

```
upload_progress_<field value>|a:5:{s:10:"start_time";...;s:5:"files";a:1:{...
```

into the session store, and the value of every part's `filename` is copied
verbatim into the nested `files` array. With `session.upload_progress.cleanup`
off the entry survives the request, so the attacker controls bytes inside
`sess_<id>` — including `<?php ... ?>`.

`templates/webroot/app/.user.ini` sets `php_serialize` for `/app`, and the lab
keeps `cleanup=Off` (in `templates/php.ini`) to make the write deterministic.

Verified output: `rce` prints `uid=33(www-data) ...`.

## 2. `include()` of the session file — verified

`vuln.php` has a target-controlled `include($_GET['page'])`. Including
`/tmp/sessions/sess_<sid>` executes the injected PHP. Session poisoning alone
only puts bytes on disk; the include sink is what turns it into code
execution. This is the honest boundary of chain 1.

## 3. Handler mismatch → object instantiation — verified

`php_serialize` stores the whole `$_SESSION` array as one serialized value;
the `php` handler expects `key|serialized` pairs. Injecting
`x|O:6:"Gadget":0:{}` into a filename puts a `|` inside the serialized array,
so the `php` reader splits there and unserializes the attacker's object.

Two details decide whether this is provable:

- The read must not carry `PHP_SESSION_UPLOAD_PROGRESS`. With that field the
  session is opened during RINIT, before userland classes exist, and the
  object can only become `__PHP_Incomplete_Class`. The CLI sends a plain GET
  for this reason.
- A decode warning is not proof. `Gadget::__destruct()` writes
  `/tmp/gadget-hit`; the chain passes only when that marker exists.

## 4. Progress-array UAF → `zend_call_function` — not reproduced

Community write-ups describe `post_bytes_processed` /
`current_file_bytes_processed` as raw `zval *` pointers cached from a hash
table that is destroyed on the next progress update, then reclaimed with
packed 320-byte strings that fake `zend_fcall_info` /
`zend_internal_function` and end in `zend_call_function`.

What we actually observed on `php:8.2.34-fpm`, with symbol deltas extracted
from that build's own binaries (`zval_ptr_dtor` / `zend_call_function`):
no RCE, no crash, unchanged worker count. The independent audit at
[xuehuolll/CVE-2026-109618-109619-audit](https://github.com/xuehuolll/CVE-2026-109618-109619-audit)
reaches the same conclusion for stock builds. Repos that claim confirmed RCE
(for example
[eness/php2shell-...-PoC](https://github.com/eness/php2shell-CVE-2026-109618-CVE-2026-109619-PoC),
whose driver carries a hard-coded `DELTA_CALL` for one Ubuntu build) were not
independently verified here, and we do not repeat their claim.

CVE-2026-109618 / CVE-2026-109619 are RESERVED at cve.org. Treat every
number-to-mechanism mapping as unconfirmed.

## 5. Aborted upload with stock `cleanup=On` — not reachable in this stack

The appealing variant is: keep the stock `cleanup=On`, abort the upload before
the multipart end event so cleanup never runs, and poison the session anyway.

Against nginx + php-fpm this did not produce a session file at all, with
`fastcgi_request_buffering` both on and off — the body has to be delivered in
full before the script runs. Apache/mod_php or a streaming stack may behave
differently. This lab therefore keeps the deterministic `cleanup=Off` path and
does not ship an abort-based chain.

## 6. Upstream notes

- [ikow/php2shell-poc](https://github.com/ikow/php2shell-poc): stdlib, no
  egress. Its lab is generated by an undocumented `lab/setup.sh`,
  `/api/endpoint.php` never calls `session_start()` (so its mismatch indicator
  cannot fire), and the compose file used `privileged: true` +
  `seccomp:unconfined`. This repository keeps the scope, drops the privileged
  flags, binds to loopback and adds the marker-based proof.
- [Zer061/CVE-2026-109618](https://github.com/Zer061/CVE-2026-109618): the
  framework's first line is prose (corrupt file), `DELTA_CALL_AUTHOR` is
  hard-coded instead of extracted with `--syms`, and its default URL points at
  a partially masked real site.

## 7. Mitigation and detection pointers

- Disabling `session.upload_progress` breaks every chain here (verified;
  [verification.md](verification.md)).
- Community rule sets: [eness/...-PoC](https://github.com/eness/php2shell-CVE-2026-109618-CVE-2026-109619-PoC)
  (Apache/ModSecurity, lighttpd, Caddy), [syhunt/php2shell-protection](https://github.com/syhunt/php2shell-protection),
  [mikensec/php2shell-lab](https://github.com/mikensec/php2shell-lab)
  (Sigma, Suricata, YARA).
- Signal ideas: session files containing `<?php` or serialized objects,
  `Failed to decode session object` warnings, multipart filenames with
  serialization syntax, php-fpm children spawning shells.
